## 0. 所有者本轮方向修正（已贯彻，作为本文档的判断前提）

**中文市场的衡量口径改变**：不再采信百度指数 / 小红书 / B站这类社会化平台信号作为"值不值得做"的依据，最终衡量标准是 **Google 搜索侧有没有真实需求**。

理由：本站获客模式是纯 Google SEO。社会化平台的需求信号即使真实存在，这个渠道也接不住——这与三角洲行动、Overwatch2 韩语两个案例是同一个教训：**需求存在，但走错了渠道**。

**对上游报告的具体推翻**：

| 上游报告的结论 | 本轮处置 |
|---|---|
| 任务B：中文"反应速度测试"需求强度 = **强**（依据：百度下拉联想密度 + B站播放量 + 小红书互动量） | **不采信为优先级依据**。这三个渠道全部是社会化平台/非 Google 生态，接不住 |
| 任务B：中文"手速测试/CPS"需求强度 = **强**，且与称号玩法匹配度全场最高 | 同上，**不采信为优先级依据** |
| 任务B：站长之家估算"反应速度测试"4.6 万/月 | 该数字是必应+百度+360+搜狗四引擎加总，**不含 Google**，不能用来判断 Google 端需求 |
| 任务A：中文两词 Semrush 无 db=cn 库、seo.web.cafe 交叉估算返回 `null` | **这才是本轮对中文的唯一有效事实**：Google 侧真实需求量级**未知** |

**由此得出的中文优先级裁决**：

> 中文市场排在验证优先级的**后面**。不是"不做中文"，而是**等英/日/韩三语跑通、拿到真实 Google 流量与排名数据之后，再决定要不要额外为中文补做一轮 Google 口径的验证**。

补充一条独立佐证，支持这个降级是对的：本站 `.rankup/baseline.md` 记录的 GSC 近 3 个月真实数据是 **韩国 775 点击（88%）/ 日本 44 / 美国 23**，中文市场（中国大陆 + 台湾）在本站历史上从未产生可见的 Google 流量。把中文排在英日韩之后，和本站自己的历史数据是一致的。

### 1.2 真实矛盾与张力（上游两份文档都没有解决，本方案必须处理）

**矛盾 A：「首页即单一产品」 vs 「多测试综合站」——哥飞同时称赞了两个相反的形态**

- testreaction 的成功原因，哥飞写得很明确：*首页汇集全站权重打内页* + *"产品只有一页，没有菜单、没有导航分心，打开就测"*。
- humanbenchmark 的成功原因，哥飞写得同样明确：*多个测试 → 交叉消费 → 停留 155s / 人均 4.4 页*。
- 而 KD 报告任务C 的建议是"合并成综合站"。

**这两条如果直接叠加，会得到一个自相矛盾的产品**：既要首页无导航、打开就测，又要多模块交叉消费。上游没有任何一份文档处理这个冲突。

→ **本方案的解法见 §3.1**（结论：首页**就是**反应速度测试本身、无顶部导航；其他模块只在**出成绩之后**的结果页出现）。这不是折中，是把两条经验各自放在它们真正生效的位置——SEO 与首屏转化靠"首页即产品"，停留与页深靠"结果页之后的交叉消费"。

**矛盾 B：`reaction time test` 的搜索量，两份文档差 3.4 倍**

| 来源 | 数值 | 口径推测 |
|---|---:|---|
| KD 报告（Semrush db=us） | **90,500 / 月** | 仅美国 |
| 哥飞 AI | **30.7 万 / 月** | 疑似全球加总，或 Ahrefs 口径 |

两个数字都指向"这是个大词"，**不影响 go/no-go**，但影响任何流量/收入测算。**列为待核实缺口**（§9 行动项 A3）：在做任何流量预期之前必须统一口径，否则会把预期做高 3 倍。

**矛盾 C：变现路径与所有者既有约束直接冲突（本案最大的未决问题）**

- 哥飞明确警告：*"测试站/小游戏站是 AdSense 限流的高发品类"*，并引用了哥飞 2025-11-12 群聊原话——被限流的"**以小游戏站居多**"。
- 哥飞给的替代方案有两条：换广告平台（adsterra），或"免费基础测试 + 付费高级报告"。
- 但所有者的既有产品约束是：**只走 SEO 获客 + 自助 SaaS/Credit 变现**。

一个免费的反应速度测试**没有任何 Credit 消耗模型**——它不调用昂贵的 API，不产出可计量的交付物，用户也没有反复付费的理由。

| 所有者约束 | 本方向是否满足 |
|---|---|
| 需求先于产品（必须已有搜索词） | ✅ 满足，且是全部候选方向里证据最硬的一个（en 90.5k / ko 135k / ja 40.5k，月度稳定长尾，非热点） |
| 只走 SEO 获客 | ✅ 满足 |
| 本人做客服可以，不要运营团队 | ✅ 满足（纯自助工具，几乎无客服面） |
| 自助 SaaS / Credit 变现 | ❌ **不满足** |

**4 条约束满足 3 条**。考虑到所有者 2026-09-13 的既有判断是"四条约束叠加后可做方向的交集接近空、待定是否放宽"，本方向是目前交集内得分最高的候选，**但变现这一条必须由所有者拍板放宽（接受广告变现）后才能进入开发**。详见 §8 go/no-go。

**张力 D：哥飞"坑四"与本站自己的历史，恰好互为反证**

哥飞说：*"技能测试类不如性格/趣味测试类容易裂变"*——这是本方向的短板。

但本站 `.rankup/baseline.md` 记录的正是硬币的另一面：SBTI 这个**性格**测试确实裂变了（2026-04 韩国病毒热潮，峰值 ~120 点击/天），然后**在一周内退潮归零**（近 28 天仅 6 点击）。哥飞自己也把"一波流热点"列为失败模式一。

→ 所以对本站所有者而言，"技能测试裂变差、但长尾稳"**恰恰是正确的方向调整**，不是缺点。裂变能力是本站已经验证过、且已经证明留不住的东西；月搜 9 万/13.5 万的稳定长尾才是本站从来没有过的东西。**称号系统的定位应当是"把长尾流量的停留和回访做厚"，而不是"再赌一次病毒传播"**——这一点上游文档的表述偏向后者，本方案予以修正。

### 1.3 本轮新增的第三方证据：站内既有反例（两份上游文档都未引用）

> **games 方向不加码**：8 游戏 × 8 原型页已建，但 GSC 无任何游戏词流量（排名 58-59 的曝光各 1 次）。

## 2. 本轮新增的一手关键词证据（Google Suggest 实测，2026-09-13）

上游报告的选词只覆盖到各语言的**核心主词**。本轮补跑了三语联想，拿到了可以直接排期的**长尾页面矩阵**，并有三项超出上游结论的新发现。

### 2.1 英语（hl=en, gl=us）

```
reaction time test → f1 | spacebar | game | world record | mobile | sound
                     | human benchmark | valorant
cps test           → cps tester | right click | mobile | 1 second | spacebar
                     | keyboard | full form
click speed test   → mobile | 1 second | spacebar | 10 seconds | keyboard
                     | right click | 5 seconds | game
```

**CPS 侧呈现出一个非常干净的程序化 SEO 矩阵**：`时长变体（1s / 5s / 10s / 60s）` × `输入方式变体（left click / right click / spacebar / keyboard / mobile）`。这是可以一次性铺出十几个独立落地页的结构，且每个变体词都被 Suggest 证实真实存在。

**英文游戏黑话核实**（Suggest 佐证，非模型记忆）：

| 词 | Suggest 证据 | 结论 |
|---|---|---|
| cracked | `cracked at fortnite`、`cracked at something meaning` | ✅ 真实游戏俚语，"极强" |
| sweaty | `sweaty gamer`、`sweaty gamer meaning`、`sweaty gamertags` | ✅ 真实，"拼命打/太较真" |
| built different | `built different meme`、`built different meaning` | ✅ 真实 meme 短语 |
| bot | `certified bot sticker cs2`、`certified bot` | ✅ 真实，CS2 圈甚至有同名贴纸 |
| aimbot allegations | **Suggest 无返回** | ⚠️ 该确切短语**不是搜索词**；仅可作为站内称号文案，不可当关键词 |

### 2.2 日语（hl=ja, gl=jp）

```
反射神経テスト → fps | ゲーム | プロゲーマー | 平均 | スマホ | ボタン
                | フレーム | f1 | 音
反応速度 テスト → 無料 | fps | スマホ | スマブラ | 音 | プロゲーマー | 陸上
                | キーボード反応速度テスト | f1反応速度テスト
VALORANT 反応速度 → テスト | 遅い | 平均 | 設定 | プロ反応速度 | キーボード反応速度
```

**新发现（重要）**：`反射神経テスト **フレーム**` 是真实联想词。日本格斗游戏/FPS 圈用**帧（1帧 = 1/60 秒 ≈ 16.7ms）**作为反应速度的自然单位。这意味着 §5 里的"帧数皮肤"**不是凭空设计的玩法，而是有实际搜索需求的表达方式**——把 240ms 换算成"14.4 フレーム"对日语用户是有信息增益的原生表达，而不是装饰。

另有 `スマブラ`（任天堂明星大乱斗）出现在联想里，说明日语市场的游戏定制化需求不限于 FPS。

### 2.3 韩语（hl=ko, gl=kr）

```
반응속도 테스트 → 디시 | 휴먼 | 사이트 | 평균 | 공식 | 1위 | 발로란트 | 동물 | 평균 디시
발로란트 반응속도 → 테스트 | 훈련장 | 사이트 | 올리기 | 연습 | 디시 | 연습 사이트 | 웹사이트 | 설정
피지컬 테스트   → 게임 | 롤 피지컬 테스트 | 마우스 피지컬 테스트 | 손가락 피지컬 테스트
```

三项新发现：

1. **`피지컬`（physical）是韩国游戏圈对"机械操作能力"的标准黑话**，`롤 피지컬 테스트`（LoL 机械操作测试）、`손가락 피지컬 테스트`（手指操作测试）都是真实联想词。**这正是本产品所测量的东西在韩语里的原生说法**，上游两份报告都没有发现这个词。应作为韩语侧的重点候选词进入正式选词流程（§9 行动项 A1）。
2. **`디시`（DCInside，韩国最大论坛）在 `반응속도 테스트` 联想中出现两次**（`반응속도 테스트 디시`、`반응속도 테스트 평균 디시`）。说明韩国用户在论坛里讨论这个测试并互相比成绩——这是**社区播种的现成入口**，也再次印证韩国是本产品最热的市场。
3. **`반응속도 테스트 1위`（反应速度测试第一名）是真实搜索词**——**排行榜需求被直接证实**。这把排行榜从"锦上添花的功能"提升为"有搜索量支撑的功能"，但它同时是本案最大的技术约束（静态站无后端，见 §7）。

另有 `동물`（动物）——"和动物比反应速度"是已被验证的内容模板，可作为低成本的内容页。

|---|---|
| "游戏定制化皮肤不作为独立 SEO 关键词页面，只作为产品内的可选皮肤/分享钩子"（原 brief 设定） | **部分推翻**。`valorant reaction time test`、`발로란트 반응속도 테스트`、`VALORANT 反応速度テスト`、`cs2 reaction time test` 都是三语真实联想词，**游戏皮肤完全可以、也应该同时作为独立落地页**。这是 arealme"一个页面一个词"打法在本案的具体落地形式 |

## 3. 产品形态定案

### 3.1 核心形态：单产品首页 + 结果页驱动的模块发现

**定案**：做**技能测试合集站**，但**入口组织方式不是"合集"**。

```
首页 /            = 反应速度测试本身（打开即可测，无顶部导航菜单）
   ↓ 用户完成一次测试
结果页（同页内切换，不跳转）
   = 成绩（ms）+ 百分位 + 称号 + 分享卡片
   + 「再测一次」
   + 「换个玩法」→ 此处、且仅此处，展示 CPS 测试等其他模块入口
```

**这个形态同时兑现了 §1.2 矛盾 A 里两条互相冲突的成功经验**：

- **首页即产品、无导航分心** → 兑现 testreaction.com 的打法（首页聚集全站权重打竞品内页；用户搜 `reaction time test` 点进来 0 阻力直接测）。
- **多模块交叉消费** → 兑现 humanbenchmark 的打法（155s 停留 / 4.4 页深），但把模块入口挪到**结果页之后**。用户此时刚拿到成绩、正处于"还想再玩一次"的兴奋点，这是转化到第二个模块的最佳时机；而在首屏放导航只会降低第一次测试的完成率。

一句话：**导航不在页面顶部，导航在成绩单下面。**

### 3.2 URL 与语言架构

第一期覆盖 **英 / 日 / 韩**三语（中文按 §0 降后处理，不在第一期）。

| 语言 | 首页主词 | 量 | KD | 来源 |
|---|---|---:|---:|---|
| 英 | `reaction time test` | 90,500/月 (db=us) | 34 | Semrush |
| 日 | `反射神経テスト` | 40,500/月 (db=jp) | 36.7 实测 | Semrush + seo.web.cafe |
| 韩 | `반응속도 테스트` | 135,000/月 (db=kr) | 37.3 实测 | Semrush + seo.web.cafe |

> 注：韩语量最大（13.5 万/月）、且 SERP 弱位证据最直接（DR0、体验分仅 5/100 的 cheheum.com 和上线 8 个月的 DR0 新站 clickreflex.com 都已进前十）。**韩语是第一期的主战场**，这与本站 GSC 历史 88% 流量来自韩国也一致。

CPS 模块的三语主词见 §3.3。页面矩阵（每个 slug 三语各一份）：

```
/                          反应速度测试（主词，首页即产品）
/cps-test                  CPS 主页（英文主词待 §3.3 定）
/cps-test/1-second         ─┐
/cps-test/5-seconds         │ 时长变体（Suggest 已验证）
/cps-test/10-seconds        │
/cps-test/60-seconds       ─┘
/cps-test/spacebar         ─┐
/cps-test/right-click       │ 输入方式变体（Suggest 已验证）
/cps-test/keyboard         ─┘
/reaction-time-test/valorant   ─┐
/reaction-time-test/cs2         │ 游戏定制页（三语均已验证，见 §5）
/reaction-time-test/f1         ─┘
/reaction-time-test/average    「平均是多少」信息页（三语 Suggest 均命中"平均/average"）
```

**语言路径**：沿用现有 next-intl `localePrefix: 'as-needed'`（英语无前缀，日韩为 `/ja/*`、`/ko/*`）。**slug 需要按语言本地化**（韩语用户不会点 `/ko/cps-test`，应为 `/ko/클릭속도테스트` 或韩语罗马化 slug）——next-intl 支持 pathname 本地化，但这是需要单独排期的一项配置工作。

**关键纪律（直接来自本站教训）**：`.rankup/decisions.md` 记录本站曾因 4,742 页薄内容矩阵导致 890 页"已抓取-尚未编入索引"，最终全线 noindex 收场。**上面的变体页矩阵必须逐页有独立内容与独立价值，不得只换一个数字复制模板**，否则会精确重演同一个事故。每个变体页至少要有：该变体独有的成绩分布数据、该变体独有的技巧说明、该变体独有的称号阈值。

### 3.3 CPS 模块三语主词（**未定案，列为阻塞项 A2**）

反应速度测试的三语主词有 Semrush 实测量级撑腰（见上表）。**CPS 模块没有——上游两份报告都没有核实过 CPS 的量与 KD**。本轮补跑了 Suggest 确认词形真实存在，但**搜索量与 KD 仍是缺口**。

| 语言 | 候选主词 | 词形是否真实 | 量级 / KD | 状态 |
|---|---|---|---|---|
| 英 | `cps test` vs `click speed test` | ✅ 两者 Suggest 均有丰富联想（本轮实测） | **未核实** | 需 A/B 定主词 |
| 日 | `連打` 系 / `クリック速度` 系 vs `CPS テスト` | 待核实 | **未核实** | 需 A/B |
| 韩 | `손속도`（手速）系 / `연타` 系 vs `CPS 테스트` | ✅ `손속도 테스트` / `손속도측정기` 经 Suggest 确认真实存在 | **未核实** | 需 A/B |

**判定这件事的关键规律（必须带进 A2 的验证）**：日韩市场**本土说法的量显著高于英文直译**，且这个规律在两个语言上同时成立：

| 对比 | 本土说法 | 英文直译 | 倍差 |
|---|---|---|---|
| 日语·瞄准 | `エイム練習` 4,400/月 | `エイムトレーニング` 140/月 | **31×** |
| 韩语·瞄准 | `에임 연습` 6,600/月 | `에임 트레이너` 590/月 | **11×** |

→ 据此**预判**（尚待数据验证）：日韩侧的 CPS 主词很可能是 `連打`/`손속도` 这类本土说法，而**不是** `CPS テスト`/`CPS 테스트`。**在 A2 出结果之前不要按英文缩写去建页**，否则会精确重演"选了直译词、量差一个数量级"的错误。

> 上游任务B 曾观察到"CPS 在中文玩家群体里已是通用黑话"——但那是**中文**的观察，且来自已被 §0 降级的社会化平台渠道，**不能外推到日韩**。

## 4. 独立域名 vs 站内板块

所有者正在另一条线上做这个决定。以下**两种情况分别给出建议**，不需要等那个决定出来。

### 4.1 先说一个必须摆在台面上的事实

本决策不是在信息真空里做的——**sbti.support 上已经做过一次同类实验，并且失败了**：

> `.rankup/decisions.md` 2026-07-18：**games 方向不加码**——8 游戏 × 8 原型页已建，但 GSC 无任何游戏词流量（排名 58-59 的曝光各 1 次）。

再叠加三条站点现状：

| 现状 | 出处 | 对"站内板块"的影响 |
|---|---|---|
| 近 28 天 6 点击 / 34 曝光，查询表近 100% 品牌词，通用词流量 ≈ 0 | `baseline.md` | **站内板块能借到的权重接近于零**。"借助已有域名权重"这个理由在本站并不成立 |
| 4,742 页 noindex，890 页"已抓取-尚未编入索引" | `decisions.md` | 域名存在爬取质量问题，新板块要和历史包袱争抢爬取预算 |
| 品牌是"Satirical Behavior Type Indicator"（恶搞人格测试） | `PROJECT.md` | 与 `reaction time test` **主题零相关**。testreaction.com 的制胜点之一恰恰是"域名本身就告诉谷歌我就是做这个的" |
| 设计系统是薄荷绿 playful-meme 风（primary `#10B981`，Space Grotesk） | `DESIGN.md` | 与电竞技能测试所需的暗色/霓虹视觉语言不匹配，套用会削弱两边 |

### 4.2 情况一：独立域名 / 独立品牌（**推荐**）

**推荐理由**：全案最强的单点证据（testreaction.com，DR3 吃下大词）的两条成因里，有一条是**精确匹配域名**，另一条是**首页即产品、无导航**。这两条在 sbti.support 的子目录下**都无法兑现**。而"借域名权重"这个站内板块的唯一优势，在本站的真实数据面前不成立（通用词流量为零）。

**需要什么**：

| 项 | 说明 |
|---|---|
| 域名 | 优先精确匹配或半匹配（对标 testreaction.com / aimtrainer.io 的命名逻辑）。**必须先查域名前世**（黑历史会直接废掉 SEO 投入）——走 rankup 的域名前世检查流程 |
| 品牌名 | 要能承载称号系统的记忆点。哥飞明确指出品牌词是第三层护城河（humanbenchmark 品牌词月搜 31.8 万贡献 47.6 万流量）。名字要短、好拼、在三语里都不拗口 |
| 技术栈 | 可直接复制 sbti-next 的技术选型（Next.js 静态导出 + next-intl + Cloudflare Pages），**但是新仓库**，不背历史包袱。详见 §7 |
| 部署 | 新建 Cloudflare Pages 项目 + GitHub Actions（照搬现有 `deploy.yml` 模式） |
| SEO 基建 | 全新：sitemap / robots / hreflang（en-ja-ko 三语互指）/ GSC + Bing 站长 / IndexNow。**韩国市场额外需要 Naver Search Advisor**——本站 P1 计划里这一条挂了很久没做（需所有者账号），在新站上是第一天就该做的事 |
| 外链 | 按哥飞口径 50–110 个引荐域即可进前十，量不大。优先 `디시`（DCInside）等韩国社区——Suggest 已证明用户在那里讨论这个测试 |
| 时间成本 | 比站内板块多约 1–2 周（域名+品牌+部署+SEO 基建），**但省掉了后面把板块拆出去重做的成本** |

**风险**：从零起权重，前 3 个月无流量是正常的，需要所有者接受这个空窗期。（缓解证据：clickreflex.com 是 DR0、上线 8 个月的新站，已经站进韩语前十。）

### 4.3 情况二：作为 sbti.support 站内新板块先验证

**这条路可以走，但必须清楚它验证得了什么、验证不了什么。**

| 能验证 | 验证不了 |
|---|---|
| 产品机制：称号系统是否触发分享、CPS 模块能否承接停留、结果页模块发现的转化率 | **SEO 可行性**。games 板块的先例 + 通用词零流量已经证明，这个域名的板块页拿不到自然流量 |
| 前端交互引擎是否好用、跨设备（手机触屏）是否可靠 | 品牌词能否积累（会积累到 SBTI 这个不相关的品牌上） |
| 三语文案与称号的实际观感 | 精确匹配域名的加成 |

**需要什么**：

| 项 | 说明 |
|---|---|
| 路由 | `app/[locale]/reaction-test/`、`app/[locale]/cps-test/`，复用现有 next-intl 与布局 |
| 文案 | 四语同步进 `messages/{en,zh,ja,ko}.json`（现有约束：文案改动必须四语同步）。**注意：这会被迫连中文一起做**，与 §0 的中文降级裁决相抵触——可以先放机翻占位并 noindex 中文版 |
| 视觉 | 需要在 `DESIGN.md` 现有薄荷绿体系内做一套暗色/电竞变体，**这是要走 DESIGN.md 修订流程的**（现有约束：不得未经批准偏离） |
| SEO | **建议直接 `noindex`**。理由：既然板块的目的是验证产品机制而非 SEO，让它进索引只会重蹈 890 页"已抓取-尚未编入索引"的覆辙，污染本已脆弱的域名 |
| 导流 | 因为拿不到自然流量，验证期的用户必须靠外部导入（韩国社区发帖 / 现有 SBTI 结果页挂入口） |
| 退出路径 | **一开始就按可迁出的方式写**：测试引擎、称号库、分享卡片全部做成独立模块，不与 SBTI 的人格类型数据结构耦合，将来整体搬去独立域名时只搬这几个目录 |

### 4.4 一句话建议

**如果目标是验证 SEO 能不能跑通（这才是本方向的核心命题）→ 走独立域名。**
**如果目标是先花最少的钱确认产品机制和称号玩法好不好玩 → 走站内板块，但必须 noindex、必须按可迁出的方式写、并且清楚它不会给出任何 SEO 结论。**

两条路不冲突，也可以串行：站内板块两周验证机制 → 独立域名正式建站。代价是多一次迁移。

## 5. 三语称号系统设计

### 5.0 分级骨架：先定阈值，再配文案

称号必须挂在**真实人群分布**上，不能凭手感切档。本轮已核实的分布数据如下。

**反应时间（视觉反应，"变色就点"口径）**

| 指标 | 数值 | 置信度 |
|---|---|---|
| 人群中位数 | 250–273 ms | 高（Human Benchmark 官方统计页） |
| 人群平均值 | 284 ms | 高（Human Benchmark） |
| 百分位 10 / 25 / 50 / 75 / 90 / 95 | 370 / 330 / 250 / 200 / 180 / 150 ms | **中**（二手汇总站，非一手） |
| FPS 职业选手典型区间 | 150–180 ms | 中 |
| 顶尖职业选手（如 TenZ） | 138–150 ms | 中 |
| 人类生理理论下限 | 80–100 ms | 中 |
| 有记录的最快（1996 Iowa） | 101 ms | 中 |
| **纯浏览器测试的可信下限** | **120 ms** | 中 |
| 系统延迟（鼠标轮询+浏览器事件+显示器） | 游戏硬件 10–30 ms / 普通电脑 50+ ms | 中 |

> ⚠️ **数据质量提醒**：中位数与平均值来自 Human Benchmark 官方统计页（一手，可信）；**百分位数列来自二手汇总站，置信度中等**。正式开发前应直接以 Human Benchmark 官方统计页的分布为准重新校准一次（§9 行动项 B1）。

**CPS（10 秒口径）**

| 指标 | 数值 | 置信度 |
|---|---|---|
| 普通人 10 秒平均 | 5–6 CPS | 高 |
| 百分位 10 / 25 / 50 / 75 / 90 | 3.5 / 5.0 / 6.5 / 8.5 / 11.0 CPS | 中 |
| 普通点击（standard click）世界纪录 | 14–16 CPS | 中 |
| 抖动点击 jitter clicking | 8–14 CPS | 中 |
| 蝴蝶点击 butterfly clicking | 15–25 CPS | 中 |
| 拖拽点击 drag clicking | 30–100+ CPS | 低 |
| **反作弊可疑线** | 持续 >20 CPS 且标准差 ≈ 0 | 低 |

> 三种技法（jitter / butterfly / drag）源自 Minecraft PvP 圈，是 CPS 这个品类的原生文化背景。**每种技法都值得一个独立说明页**，这是纯内容型的长尾页面来源，也是"信息增益"的天然素材。

**七档阈值（本方案采用）**

```
反应时间 (ms)   >350 | 310-350 | 270-310 | 230-270 | 180-230 | 150-180 | 120-150 | <120(存疑)
CPS (10s)       <3.5 | 3.5-5.0 | 5.0-6.5 | 6.5-8.5 | 8.5-11  | 11-14   | 14-20   | >20(存疑)
人群占比         最慢10% | ~15%  | ~25%    | 中间25% | ~15%    | ~5%     | ~4%     | ~1%
```

**最高一档故意设计成"疑似开挂"而不是"精英"**——理由见 §5.1。这一档同时承担**反作弊提示**功能（浏览器测试低于 120 ms 在物理上就不可信），把一个技术必需的免责声明变成了产品里最好笑、最想被截图的那一格。

### 5.1 英语：跳出 Beginner→Elite 的公司考评腔

**先说差异化在哪。** ReflexLab 那类 `Beginner → Novice → Average → Good → Great → Elite` 是一套**职级评语**：它准确、礼貌、毫无情绪，也毫无分享价值。没有人会截图"你的等级：Good"。

本方案的三条差异化原则：

1. **用真实英语游戏俚语，不用考评词**。全部词已用 Google Suggest 反查确认真实存在（§2.1），不是模型编的。
2. **顶格不是褒奖，是"被举报"**。在 FPS 文化里，**被队友指控开挂是最高级别的赞美**。把最高档命名为"疑似开挂"而不是"Elite"，制造的是一个梗，不是一个评语——而梗才会被截图。这个概念在三种语言里**同时成立**（英 hacker/aimbot、日 チート、韩 핵），所以它能做成全站统一的顶格设计，而不是只在英文里好笑。
3. **底格是自嘲，不是羞辱**。给真实用户贴标签，侮辱性词汇会让人关掉页面而不是分享。`Certified Bot` 之所以安全，是因为"bot"在 CS2 语境里是玩家之间互相调侃的日常用语（Suggest 实证：`certified bot sticker cs2`），语气是损友式的，不是人身攻击。

**英语称号阶梯（反应速度，8 档）**

| 档 | ms | 称号 | 语感/出处 | 结果页副文案方向 |
|---:|---|---|---|---|
| 1 | >350 | **Certified Bot** | CS2 圈日常互损；`certified bot sticker cs2` 实证存在 | "移动靶都比你先开枪。" |
| 2 | 310–350 | **Still Loading** | 加载中 = 反应慢的通用梗 | "你的神经在排队。" |
| 3 | 270–310 | **Casual Enjoyer** | `enjoyer` 是真实后缀梗 | "周末打两把那种。" |
| 4 | 230–270 | **Certified Human** | 呼应人群中位数 250–273ms | "你就是那条平均线。" |
| 5 | 180–230 | **Sweaty** | `sweaty gamer` 实证存在 | "你已经开始较真了。" |
| 6 | 150–180 | **Cracked** | `cracked at fortnite` 实证存在；职业选手区间 | "职业选手就在这一档。" |
| 7 | 120–150 | **Built Different** | `built different meme` 实证存在 | "有记录的人类最快是 101ms。" |
| 8 | <120 | **Suspected Hacker** | 顶格即梗；同时是反作弊提示 | "浏览器测不出这个数。要么你抢跑了，要么该被举报了。" |

**CPS 侧复用同一套阶梯**，但第 7 档换成技法命名（`Butterfly Merchant` / `Jitter Addict`），第 8 档 `Autoclicker Allegations`——因为 CPS 圈的"作弊"指控有具体对象（自动点击器），比泛指的 hacker 更贴题。

> 使用纪律：`Suspected Hacker` / `Autoclicker Allegations` 只作为**站内称号文案**。Suggest 实测 `aimbot allegations` 无返回，**不是搜索词，不得用作关键词或 title**。

### 5.2 日语

本轮对 brief 里提示的候选词做了一手语料核实（ニコニコ大百科 / ピクシブ百科事典 / goo辞書 / Google Suggest）。**结果推翻了 brief 里的两个假设**：

| brief 提示的词 | 核实结果 | 处置 |
|---|---|---|
| **覚醒者** | ❌ **不是玩家称呼**。只是角色状态名/卡牌名/技能名（ラングリッサー、デュエルマスターズ 等作品设定词），游戏圈不用它称呼人 | **弃用** |
| **廃人** | ⚠️ 真实存在，但语感双面：原义"为游戏搭上人生"的贬义/自嘲，现部分场合带敬意，**仍可能被读成"废人/沉迷者"** | **不作主推**，最多作彩蛋 |
| 雑魚 / ザコ | ⚠️ 真实且高频，但 Suggest 直接返回 `雑魚はゲームやめろ`（菜鸡快退游）这类**真实骂战用例** | **弃用**（冒犯风险实测存在） |
| 下手くそ | ⚠️ 强侮辱性。Suggest 出现 `下手くそ 言い換え`（找委婉说法）——用户自己都在找替代词 | **弃用** |
| 人間卒業 | ✅ 真实存在于音游/弹幕射击圈，强褒义的自嘲式最高赞美 | **采用为顶格** |
| 神プレイ / 猛者 / 達人 / 化け物 | ✅ 全部一手证据确认，褒义、无冒犯 | **采用** |

**一个必须承认的不对称**：§5.1 给英语定的原则是"底格用自嘲式俚语"，但日语里**语料证据显示，好笑的低分词全都是真的会冒犯人的词**。所以日语阶梯采用**不对称设计——底部中性、越往上越梗**。这不是偷懒，是跟着证据走：强行在日语底格塞俚语只会让用户关页面。

### 5.3 韩语

**本轮对 brief 提示的方案做了三处重要修正**，都基于一手语料（나무위키 / 국립국어원 / 인벤 / Naver）：

| brief 的提示 | 核实结果 | 处置 |
|---|---|---|
| 用 `핵-` 作递进前缀 | ⚠️ **高歧义风险**。`핵-` 作强调前缀确实存在（핵고수 = 超厉害的高手），但在**游戏圈**里 `핵` 的主流义项是**外挂/作弊**（핵쟁이 = 开挂的人、게임핵 = 外挂程序） | **弃用 `핵-`** |
| 用 `존버` 作称号 | ⚠️ 词真实，但**语境完全相反**。존버 = "死扛硬撑/长期不动"（源自星际猥琐蹲守或股市死扛），核心是**忍耐与静止**，跟"手快"方向相反 | **弃用** |
| 用 `여포` 作称号 | ⚠️ 词真实，喻"某领域最强者"，但核心是**战斗力/攻击性**不是**反应速度**；最出名用法还是 `방구석 여포`（键盘侠），带贬义联想 | **弃用** |

**为什么 `핵-` 在本产品上的风险比一般场景更高**（这是本轮最重要的一条修正）：称号是**脱离语境、单独展示**的标签，不像句子里有上下文帮忙消歧。而本产品恰恰是**速度测试**——当分数快到夸张时，韩国玩家的第一反应本来就是"这是不是开挂了"。在这个场景下给用户贴 `핵고수`，会被读成**阴阳怪气的作弊指控**，而不是夸奖。

**安全替代前缀**（均已核实真实、无歧义）：`초-`（超-，最中性安全）、`갓-`（god，褒义强调，源自英语 god 经日语「神ゲー」传入韩语）、`개-`（强调前缀，真实高频，代价是自带口语糙感）。

| 档 | 称号 | 罗马音 | 语感 |
|---:|---|---|---|
| 1 | 쌩초보 | ssaeng-chobo | 自嘲"纯新手"，零冒犯 |
| 2 | 하수 | hasu | 中性/轻自嘲，"下手" |

| 5 | 초고수 | cho-gosu | 褒义加强（`초-` 安全无歧义） |
| 6 | 갓고수 | gat-gosu | 褒义，"神级高手" |
| 7 | 피지컬 괴물 | pijikeol goemul | 强褒义，"反应/操作怪物级" |
| 8 | 레전드 | rejeondeu | 顶格，"传说级"，零歧义 |

> ⚠️ `갓손`（神之手）是基于 `갓-` 构词规律的**推断组合，未逐字独立验证**，本表已改用证据更硬的 `갓고수`。若要用 `갓손`，上线前需单独核实一次（§9 行动项 B4）。

### 5.4 一个跨语言的结构性发现

`피지컬`（韩）和 `フィジカル`（日）是**同一个外来词**，在两种语言里都指"反应速度 + 操作精度的综合身体能力"，且都是电竞圈的核心评价词（韩语源自星际争霸解说文化）。

**英语里反而没有一个对等的单词**——英语要表达同一个意思，只能用 `mechanics`、`aim`、`reflexes` 这些分开的词。

这个不对称有两个直接用处：

1. **日韩两个市场可以共用同一套产品概念叙事**（"测你的フィジカル/피지컬"），文案与视觉可以高度复用，只换语言层。
2. **韩语侧 `피지컬` 词族（`롤 피지컬 테스트`、`손가락 피지컬 테스트`）是一条未被上游报告发现的关键词通道**，需要正式验证量级（§9 行动项 A1）。

另外韩语侧 `손속도`（手速）、`APM` 都是真实存在的量化俗语，且 `손속도 테스트`/`손속도측정기` 已有真实搜索——**这些是 CPS 模块在韩语里的原生落地词**，优先级应高于英文缩写 `CPS 테스트`（与日韩"本土说法 > 英文直译"的既有规律一致）。

## 6. 游戏定制化皮肤方案

### 6.0 选皮肤的原则：按已验证的搜索需求选，不按喜好选

原 brief 的设定是"皮肤不作为独立 SEO 关键词页面，只作为产品内的可选皮肤/分享钩子"。**§2 的 Suggest 实测推翻了这个设定的前半句**——皮肤对应的游戏词本身就是三语真实搜索词：

| 皮肤 | 英 | 日 | 韩 | 证据 |
|---|:--:|:--:|:--:|---|
| VALORANT | ✅ | ✅ | ✅ | `reaction time test valorant` / `VALORANT 反応速度テスト` / `발로란트 반응속도 테스트` |
| CS2 | ✅ | — | — | `cs2 reaction time test`、`cs2 reaction time map` |
| 起跑灯（F1） | ✅ | ✅ | ✅ | `f1 reaction time test`（含 with sound / world record / average）/ `f1 反応速度テスト` / `반응속도 0.0001초 f1 드라이버` |
| 格斗游戏帧 | — | ✅ | — | `反射神経テスト フレーム` |
| LoL / 피지컬 | — | — | ✅ | `롤 피지컬 테스트`、`손가락 피지컬 테스트` |
| 大乱斗 | — | ✅ | — | `反応速度 テスト スマブラ` |

**所以皮肤是双重身份**：站内的可选玩法 + 站外的独立落地页（arealme"一个页面一个词"打法的具体落地）。**没有搜索证据的皮肤不做**——这条纪律防止把开发时间花在自嗨的皮肤上。

### 6.1 皮肤一：VALORANT / FPS 模式（三语全覆盖，优先级最高）

| 项 | 设计 |
|---|---|
| 场景改写 | 不再是"屏幕变绿就点"，而是"**掩体后探头，敌人出现就开枪**"。同样的计时内核，完全不同的叙事 |
| 视觉 | 暗色 + 准星 + 命中判定闪光；替换掉默认的色块 |
| 称号改写（英） | >350ms `Whiffed the Op` / 230–270ms `Silver Lobby Regular` / 150–180ms `First Blood Machine` / <120ms `Ban This Account` |
| 场景文案 | "243ms — 一个突进型角色冲进你准心，还是跑掉了。" |
| 落地页主词 | en `reaction time test valorant` · ja `VALORANT 反応速度テスト` · ko `발로란트 반응속도 테스트` |
| 页面独有内容 | 该游戏的职业选手反应时间对照、`발로란트 반응속도 올리기`（怎么提升）这类衍生长尾的实质解答 |

### 6.2 皮肤二：格斗游戏「帧」模式（日语专属，信息增益最高）

这是本方案里**唯一一个把原始数字换算成用户真正想知道的答案**的皮肤，也是日语市场的差异化武器。

| 项 | 设计 |
|---|---|
| 核心机制 | 把 ms 换算成 **帧**（60fps 下 1 帧 ≈ 16.7ms）。240ms = **14.4 フレーム** |
| 为什么有价值 | 日本格斗游戏圈用帧数讨论一切。"你的反应是 240 毫秒"不解决任何问题；"**你反应不了 14 帧以内的中段**"直接回答了玩家真正的问题。这是典型的 Information Gain——同样的数据，别人没给出这个解读 |
| 场景文案 | "あなたの反応：**14.4F**。20F の中段は見えるが、14F の下段は無理。" |
| 结果页附加 | 一张「各帧数技能你能不能反应」对照表——这张表本身就是可被引用、可被 AI 搜索抓取的结构化内容 |
| 落地页主词 | ja `反射神経テスト フレーム`（Suggest 已验证） |
| 风险 | 帧数对照需要真实格斗游戏的帧数常识支撑，写错会被核心玩家一眼识破。**文案必须找懂格ゲー的人过一遍**（§9 行动项 B3） |

### 6.3 皮肤三：起跑灯模式（英日韩三语都有需求，且自带最优雅的反作弊设计）

| 项 | 设计 |
|---|---|
| 核心机制 | 五盏红灯依次亮起 → 全灭 → 尽快反应。这是全世界辨识度最高的反应测试形式 |
| **为什么特别** | 赛车规则里，起步反应快过约 **0.2 秒**会被判**抢跑罚时**（needs-verify，见下）。这意味着这个皮肤**自带一条官方的"太快 = 犯规"规则**，和 §5.0 里"<120ms 在浏览器上不可信"的反作弊设计是同一个形状。别的皮肤需要解释为什么太快要被标记，这个皮肤不需要解释——规则本来就这样 |
| 称号改写（英） | 抢跑档 `Jump Start — Penalty` / 顶档 `Pole Position` / 中档 `Midfield` / 底档 `Formation Lap` |
| 场景文案 | "灯灭后你用了 0.31 秒。发车时你已经掉到第 11 位了。" |
| 落地页主词 | en `f1 reaction time test`（衍生：`with sound` / `world record` / `average` 各自可独立成页）· ja `f1 反応速度テスト` |
| 待核实 | 0.2 秒抢跑阈值属于常识性记忆，**置信度中**，正式文案前需核实赛事规则原文（§9 行动项 B2） |

### 6.4 皮肤四：LoL / 피지컬 模式（韩语专属）

| 项 | 设计 |
|---|---|
| 为什么做 | `피지컬` 是韩国游戏圈对"机械操作能力"的标准说法，`롤 피지컬 테스트` 是真实联想词。**这是本产品在韩语里的原生名字**，比直译的"반응속도"更贴玩家自我认知 |
| 场景改写 | "非指向性技能飞来 → 及时交闪现" |
| 场景文案 | "0.28 초. 논타겟 스킬 보고 플래시? 아직 무리다." |
| 称号体系 | 用韩语前缀递进结构（见 §5.3） |
| 落地页主词 | ko `롤 피지컬 테스트` / `피지컬 테스트`（需先做正式量级验证，§9 行动项 A1） |

### 6.5 ⚠️ 知识产权纪律（上游文档均未提及，必须在开发前定规矩）

VALORANT、CS2、LoL、F1、スマブラ 全部是**他人注册商标**。本方案的用法必须限定在描述性使用范围内：

| 允许 | 禁止 |
|---|---|
| 在 title/正文里以**描述性**方式提及游戏名（"reaction time test for Valorant players"） | 把游戏名/厂商名做成**域名、品牌名、Logo** |
| 自制的、不含任何原作素材的视觉风格 | 使用官方 Logo、角色立绘、UI 截图、字体、音效 |
| 引用公开的职业选手数据并注明出处 | 暗示与厂商有合作、授权或官方背书 |
| 通用词描述（"突进型角色"、"非指向性技能"） | 直接用角色名做称号（如把称号叫某个具体英雄的名字） |

页脚需要一句标准声明：本站与上述游戏的权利人无关联，所有商标归各自所有者。**这一条应在建站第一天就落地**，不要等收到通知再补。

## 7. 技术实现工作量级判断

结论基于对 sbti-next 的只读架构评估（Next.js 16 App Router + next-intl + Tailwind 4 + zustand，`output: 'export'` 纯静态导出，部署 Cloudflare Pages）。

### 7.1 一句话结论

**两个测试模块本身是小功能，不是难点。真正的架构瓶颈是排行榜和动态分享图——它们要求一个这个项目完全不存在的后端。**

### 7.2 分层复用表

| 层 | 现状 | 反应速度测试 | CPS 测试 | 需新增 |
|---|---|---|---|---|
| 路由 | App Router，`app/[locale]/...`，19 个 page，**无 `app/api`** | 复用约定 | 复用约定 | 各一个新 page；sitemap/导航/hreflang **三处均需手动登记**（非自动扫描） |
| i18n | next-intl，zh/en/ja/ko，`messages/{locale}.json` 24 namespace | 整套复用 | 整套复用 | 三语称号文案（**主要工作量是内容不是代码**） |
| 状态管理 | 双轨：主测试用 zustand；后加的 8 个游戏测试已改用组件内 `useState` | 跟随游戏测试先例，本地 state 计时 | 本地 state / `useRef` 计数 | 各一个纯函数 scoring/tier 映射 |
| 结果页 | `result-phase.tsx` 有 `GameV2Result`（props 驱动，解耦） | 布局壳复用 | 布局壳复用 | 新数值结果卡（照抄 props 驱动写法） |
| 称号数据结构 | 现有 `personalities.json`/`ArchetypeV2` 都是"多维画像→离散分类"，**假设不成立**（本产品是单一数值） | 需新设计 | 需新设计 | `TierDefinition{ minMs/maxMs, title: LocalizedText }`——`LocalizedText` 类型可直接复用 |
| 分享（文字/链接） | `share-buttons.tsx`，纯 URL intent，与测试类型完全解耦 | **零改动复用** | **零改动复用** | 无 |
| 分享图（用户手动存图） | `save-result-image.tsx`，Canvas2D 手绘 → 下载 PNG | 模式复用，画布内容重写 | 同左 | 新 Canvas 绘制函数 |
| **动态 OG 图（链接预览随成绩变化）** | 全站唯一一张静态 `og-default.png`，**零 satori / `@vercel/og` / `opengraph-image.tsx`** | ❌ **不支持** | ❌ **不支持** | 独立 Worker + ImageResponse 类方案 |
| 存储（个人历史/最佳成绩） | `lib/history.ts`，纯 localStorage | 完全复用 | 完全复用 | 无 |
| **存储（排行榜）** | **无 D1 / KV / R2 / API 路由，零后端** | ❌ **不支持** | ❌ **不支持** | 独立 Worker + D1 |
| 测试 | vitest `environment: 'node'`，只测 `lib/**/*.test.ts`，9 文件 167 用例；**CI 不跑测试** | 纯函数测试可复用范式 | 同左 | 要测点击计时需新增 jsdom + testing-library |

### 7.3 工作量级

| 项 | 量级 | 说明 |
|---|---|---|
| 反应速度测试模块 | **1–2 天** | 核心逻辑极简（随机延迟 + 点击时间差）。工作量集中在套壳：路由、i18n、sitemap、导航、结果卡、抢跑判定分支。**技术零风险** |
| CPS 测试模块 | **1–2 天** | 逻辑更简单（限时计数），UI 状态略多。**与反应速度模块一起做时，第二个的边际成本明显更低**——两者共享结果卡范式、分享按钮、tier 结构 |
| 称号系统 | **半天–1 天** | 只是"数值区间 → 称号"的数据结构 + 三语文案，复用现成 `LocalizedText`，**架构上毫无障碍** |
| 分享图（用户自己存图发出去） | **半天–1 天** | 照抄现有 Canvas2D 套路换内容 |
| **排行榜 / 动态 OG 图** | **1–2 周起，独立子项目量级** | 见 §7.4 |

**第一期（反应速度 + CPS + 称号 + 存图分享）合计：约 4–6 天开发**，外加三语文案与 SEO 落地页内容（内容工作量另计，且很可能超过开发工作量）。

> 对照上游报告任务C 的判断："反应速度与手速测试两个引擎几乎同构，合并成本极低"——**架构评估证实了这一点**。

### 7.4 真正的瓶颈：排行榜与动态分享图

上游报告把"称号/计分/分享/排行榜"笼统归为"可复用的结果处理层，边际成本很低"。**架构评估推翻了其中的排行榜一项**：

- 排行榜 和 动态 OG 图 本质是**同一类问题**：都要求"按请求实时计算并返回结果"。
- 而本项目是彻底的静态导出站，`@cloudflare/next-on-pages` 虽然装了但**实际没用**，是死依赖。
- 这不是"在现有代码上顺手加一块"，而是**必须新增一整个后端子系统**。

**⚠️ 一个必须先澄清的需求歧义**："分享图"这个词指两种完全不同的东西，成本差一个数量级：

| 含义 | 成本 | 现有架构 |
|---|---|---|
| 生成一张图，**用户自己下载后发到社群** | 半天 | ✅ 立等可用 |
| **粘贴链接后自动显示该用户成绩的预览图** | 1–2 周 | ❌ 需新建后端 |

哥飞咨询里引用的那条经验——*"分享图里的二维码是一个小细节，但它能把传播链路接起来"*——指的是**第一种**（用户手动传播的图片里带回访入口）。**第一期做第一种就够，不要误升级成第二种。**

**但排行榜是另一回事**：§2.3 的 Suggest 实测发现 `반응속도 테스트 1위`（反应速度测试第一名）是真实韩语搜索词。**需求方最贵的功能恰好是有搜索量支撑的功能**。处理建议：

1. **第一期不做全局排行榜**，用 localStorage 做"你的历史最佳"（零成本，已有 `lib/history.ts` 范式），先验证用户是否真的反复测。
2. **第二期**若数据证明有粘性，再新增独立 Cloudflare Worker + D1 做全局榜。**用 D1 不用 KV**（排行榜需要排序查询）。
3. **不要为此把 sbti-next 整体切到 next-on-pages**——那条路未经验证、改动面大、风险远高于旁路一个 Worker。

### 7.5 架构风险与绕过方案

| 风险 | 绕过 |
|---|---|
| `output: 'export'` 无任何服务端能力 | 新增**独立** Cloudflare Worker（+D1）作旁路后端，静态页 `fetch()` 调用。不要改造主项目的渲染模式 |
| `strip-rsc-payloads.mjs` 是为压到 Cloudflare Pages **2 万文件上限**而存在，副作用是全站 `<Link>` 预取已关闭 | 两个新页面增量很小不会撞限；但**若给每个分数区间生成独立静态页会文件数暴涨**，§3.2 的变体页矩阵要控制规模 |
| 静态导出下无 `middleware.ts`，语言路由全靠构建期 `generateStaticParams` | 新页面照抄 `app/[locale]/test/page.tsx` 的静态化写法，不引入运行时 locale 判断 |
| sitemap 手写列表、导航硬编码数组、hreflang 需显式调用 `buildAlternates()` | **开发 checklist 必须显式列出这三处**，否则新页面漏登记——本站已有页面漏登记的历史 |
| CI 只跑 build + deploy，**不跑测试也不跑 typecheck** | 顺手在 workflow 加 `pnpm test` / `pnpm typecheck`，成本极低 |
| vitest 是 `node` 环境，无法测点击计时精度 | 为新模块单开一个 vitest project 加 jsdom，不影响现有 lib 层测试 |
| **计时精度本身**：浏览器 `performance.now()` 受显示器刷新率、`requestAnimationFrame` 节流、系统延迟影响，实测会给结果加 10–50ms | 结果页必须有明确免责说明；**不同设备的成绩不可直接比较**——这也是全局排行榜在公平性上的固有缺陷，再次支持第一期不做全局榜 |

## 8. go / no-go 结论

### 8.1 裁决：**有条件 GO**

**产品与 SEO 层面：GO，且是目前所有候选方向里证据最硬的一个。**
**商业层面：卡在一个所有者必须先拍板的决策上，未决之前不应进入开发。**

拆开说：

| 维度 | 判定 | 依据 |
|---|---|---|
| 需求是否真实存在 | ✅ **GO** | 三语主词 Semrush 实测：en 90,500 / ko 135,000 / ja 40,500 月搜；且是**长尾稳流**不是热点 |
| 新站能否挤进前十 | ✅ **GO** | 8 个 KD/SERP 组合里 7 个判"有现实机会"；两个独立数据源确认 testreaction.com 以 DR≈3 排到大词第 2；链接预算仅 50–110 引荐域 |
| 产品形态是否成立 | ✅ **GO** | §3.1 已解决"首页即产品 vs 多测试综合站"的矛盾；humanbenchmark 与 testreaction 两条经验各归其位 |
| 称号系统能否落地 | ✅ **GO** | 三语阶梯已基于一手语料设计完毕，且剔除了会冒犯用户的词；架构上零障碍（半天工作量） |
| 技术可行性 | ✅ **GO** | 第一期约 4–6 天开发；真正的瓶颈（排行榜/动态 OG）已被识别并**移出第一期** |
| 游戏皮肤差异化 | ✅ **GO**，且**优于预期** | 皮肤词经三语 Suggest 验证有独立搜索需求，可同时作为落地页，而非仅作站内装饰 |
| **变现路径** | ❌ **NO-GO（阻塞项）** | 见下 |

### 8.2 唯一的硬阻塞：变现

这是本方案唯一一个"不是靠再做一轮调研就能解决"的问题，必须由所有者做一个取舍：

- 所有者既有约束是 **自助 SaaS / Credit 变现**。一个免费的反应速度测试**没有 Credit 消耗模型**——不调用昂贵 API，不产出可计量交付物，用户没有反复付费的理由。
- 这个品类现实中的变现方式就是**广告**（humanbenchmark、arealme、绝大多数 CPS 站都是广告变现）。
- 而哥飞明确警告：**测试站/小游戏站是 AdSense 限流的高发品类**，群里确认"被提示的以小游戏站居多"。替代方案是 adsterra 一类，或"免费测试 + 明码标价的一次性付费高级报告"（**必须避开 Stripe 重点打击的隐藏订阅陷阱**）。

**所以决策是二选一：**

- **A. 放宽变现约束，接受广告变现** → 本方向立即可执行，是当前约束交集里得分最高的候选（4 条约束满足 3 条）。
- **B. 坚持 Credit/SaaS 变现** → 本方向 **no-go**，因为它在商业模型上根本不是一个 SaaS。

参考：所有者 2026-09-13 的既有判断是"四条约束叠加后可做方向的交集接近空、待定是否放宽纯 SEO"。**本方向的价值恰恰在于它把这个抽象的取舍变成了一个具体的、有完整方案垫背的选择题**——不是在真空里讨论要不要放宽约束，而是"这个已经论证到可执行的方案，要不要因为变现这一条放掉"。

### 8.3 这份方案算不算"可以直接拿去执行"

**算，但有一个商业闸门和三个选词缺口。**

- 产品形态、URL 架构、三语称号、皮肤方案、技术路径、工作量级——**全部已定案，可直接排期**。
- 但在写第一行代码之前，必须先过 §8.2 的变现决策，并补完 §9.A 的三个选词缺口（否则会出现"页面建好了但主词选错"的返工）。
